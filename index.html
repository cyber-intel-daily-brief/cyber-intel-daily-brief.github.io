1. Optimizely Web Experimentation ถูกใช้เป็นช่องทางกระจาย JavaScript อันตราย

Optimizely ยืนยันว่าผู้ไม่ได้รับอนุญาตใช้ช่องโหว่เพิ่ม JavaScript อันตรายในโครงการของลูกค้าบางส่วน ก่อนแก้ช่องโหว่และนำโค้ดออกแล้ว

สถานการณ์

Optimizely ระบุในหน้าสถานะว่าพบเหตุด้านความมั่นคงปลอดภัย ซึ่งผู้ไม่ได้รับอนุญาตใช้ช่องโหว่ในผลิตภัณฑ์ Experimentation เพื่อเพิ่ม JavaScript อันตรายลงในโครงการของลูกค้าบางส่วน งานวิจัยภายนอกตรวจพบโค้ดใน Snippet ของหลายองค์กรและหลายอุตสาหกรรม โดยโค้ดถูกส่งผ่านเส้นทางที่เว็บไซต์เชื่อถืออยู่เดิม เหตุนี้จึงเป็นความเสี่ยงแบบ Supply Chain ที่อาจกระทบผู้เข้าชมเว็บไซต์ปลายทาง

ผลกระทบ

Optimizely แก้ช่องโหว่ นำโค้ดที่ถูกแทรกออก รักษาความปลอดภัยบัญชีที่ได้รับผลกระทบ และเพิ่มมาตรการป้องกันแล้ว อย่างไรก็ดี เว็บไซต์ที่ใช้ Optimizely ควรถือว่าช่วงเกิดเหตุอาจมี Script ที่ไม่ได้รับอนุญาตทำงานใน Browser ของผู้ใช้ และต้องตรวจ Log กับการเปลี่ยนแปลงโครงการของตนเอง ไม่ควรอนุมานรายชื่อลูกค้าหรือข้อมูลที่ถูกขโมยนอกเหนือจากหลักฐานของแต่ละองค์กร

ข้อเสนอแนะ

ตรวจ Optimizely Project JavaScript และประวัติการแก้ไขย้อนหลัง หมุนเวียน Credential ของผู้ดูแลที่เกี่ยวข้อง ตรวจ Web Analytics, CSP Report และเหตุผิดปกติฝั่ง Browser ในช่วงเวลาเกิดเหตุ บังคับใช้ Content Security Policy แบบ Allowlist และลดสิทธิผู้แก้ไขโครงการ พร้อมติดตามคำแนะนำเฉพาะจาก Optimizely

2. RIKEN ระงับ Fugaku หลังตรวจพบการเข้าถึงโดยไม่ได้รับอนุญาตและข้อมูลผู้ใช้อาจรั่ว

RIKEN ระบุว่าไฟล์ใน Home Directory และข้อมูลยืนยันตัวตนอาจถูกนำออก กระทบผู้ใช้ Fugaku สูงสุด 4,222 ราย และ RIKYU สูงสุด 375 ราย

สถานการณ์

RIKEN ยืนยันว่าระบบที่เกี่ยวข้องกับการดำเนินงานซูเปอร์คอมพิวเตอร์ Fugaku ถูกบุคคลภายนอกเข้าถึงโดยไม่ได้รับอนุญาต การสอบสวนพบว่าผู้โจมตีใช้หน้า Dashboard สถานะที่เข้าถึงได้จากสาธารณะเป็นเส้นทางเข้าสู่เครือข่ายปฏิบัติการภายในระหว่าง 10–13 พฤศจิกายน โดยวิธีเจาะที่แน่ชัดยังอยู่ระหว่างสอบสวน

ผลกระทบ

ไฟล์ใน Home Directory ตลอดจนชื่อ อีเมล รหัสผู้ใช้ และ Credential ที่ผู้ใช้เก็บไว้เพื่อเชื่อมต่อระบบภายนอก ถูกนำออกหรืออาจถูกนำออก RIKEN ประเมินผู้ใช้ Fugaku สูงสุด 4,222 รายและ RIKYU สูงสุด 375 รายอาจได้รับผลกระทบ แต่ยังไม่พบหลักฐานชัดเจนว่าข้อมูลงานวิจัยถูกนำออก องค์กรได้ระงับ Fugaku ปิดการเข้าถึงจากภายนอก แยกระบบ และเปลี่ยน Administrative Key

ข้อเสนอแนะ

หน่วยงานที่มีผู้ใช้ Fugaku หรือ RIKYU ให้เพิกถอน Public Key และ Credential ภายนอกที่เคยเก็บบนระบบ ตรวจการใช้งานบัญชีและระบบปลายทางย้อนหลังตั้งแต่ 10 พฤศจิกายน และประสานผู้ใช้ที่ได้รับแจ้ง สำหรับโครงสร้างพื้นฐานวิจัยทั่วไปควรแยก Dashboard สาธารณะออกจากเครือข่ายบริหารและจำกัด Secret ที่เก็บใน Home Directory

3. Uber แจ้งผู้ขับขี่เกือบ 150,000 รายได้รับผลกระทบจากเหตุของ Fireworks AI

Uber แจ้งหน่วยงานกำกับในสหรัฐฯ ว่าผู้ให้บริการรายหนึ่งแจ้งเมื่อ 9 ตุลาคมว่าบุคคลภายนอกได้ Credential ภายในของผู้ให้บริการและใช้เข้าถึงบัญชี Uber ที่อยู่กับบริการดังกล่าว สื่อรายงานว่าผู้ให้บริการคือ Fireworks AI และหนังสือแจ้งในรัฐ Oregon ระบุจำนวนผู้ได้รับผลกระทบรวม 149,346 ราย เหตุนี้เป็นการอัปเดตขอบเขตจากข้อมูลเบื้องต้นที่เผยแพร่ก่อนหน้า

ผลกระทบ

ข้อมูลที่เกี่ยวข้องประกอบด้วยภาพใบขับขี่และข้อความที่สกัดจากภาพ ได้แก่ ชื่อ ที่อยู่ วันเกิด และเลขใบขับขี่ ผู้โจมตีใช้ Credential ภายในของผู้ให้บริการ จึงไม่กระตุ้นการแจ้งเตือนที่อาศัยพฤติกรรม Login ของลูกค้าตามคำชี้แจงที่เผยแพร่ ความเสี่ยงหลักคือการสวมรอยและ Phishing ที่อ้างข้อมูลส่วนบุคคลจริง

ข้อเสนอแนะ

ผู้ได้รับแจ้งควรใช้บริการติดตามเครดิตตามที่บริษัทเสนอ ตรวจบัญชีและระวังข้อความอ้างการยืนยันตัวตน องค์กรที่ใช้ AI SaaS ควรสำรวจ Dataset และ Credential ที่ฝากกับผู้ให้บริการ บังคับใช้ Export/Access Logging แยก Secret ต่อ Tenant และกำหนดเหตุจาก Vendor Credential เป็นกรณีที่ต้องแจ้งเตือนด้วย

4. Tor ออก 0.4.9.17 เร่งด่วนเพื่อเสริมการป้องกัน DDoS ที่กระทบ Relay ส่วนใหญ่

TorDDoSNetwork Resilience

Tor Project ระบุว่า Relay ทั่วเครือข่ายถูกกดดันจาก Client Circuit จำนวนมาก และขอให้ผู้ดูแล Relay อัปเกรดเป็น 0.4.9.17 โดยเร็ว

สถานะ: Security Update Available; Attack Ongoingเผยแพร่: 13–17 พ.ย. 2569
ดูรายละเอียดสถานการณ์ ผลกระทบ และข้อเสนอแนะ

สถานการณ์

Tor Project ออก Tor 0.4.9.17 พร้อมชุดแก้ไขด้านความมั่นคงปลอดภัย โดยระบุว่าการแก้ไขหนึ่งรายการสำคัญต่อการป้องกัน Denial-of-Service ของ Relay ที่เกี่ยวกับการจัดการ IPv6 การออกเวอร์ชันนี้เป็นการตอบสนองอย่างรวดเร็วต่อ DDoS ที่กำลังเกิดและกระทบผู้ดูแล Relay ส่วนใหญ่

ผลกระทบ

Relay หลายแห่งถูก Client Circuit จำนวนมหาศาลกดดัน ทำให้เสถียรภาพและความพร้อมใช้งานของเครือข่ายได้รับผลกระทบ Tor Project ยังประเมินมาตรการเพิ่มเติมและคาดว่าจะมีเวอร์ชันต่อเนื่อง แหล่งต้นทางไม่ได้ระบุผู้โจมตีหรือเวลาเริ่มต้น จึงไม่ควรระบุ Attribution เพิ่มเติม

ข้อเสนอแนะ

ผู้ดูแล Tor Relay ให้อัปเกรดเป็น 0.4.9.17 โดยเร็วและติดตามประกาศรุ่นถัดไป ตรวจ CPU, Memory, Circuit Build และ Network Saturation หลังอัปเดต องค์กรที่พึ่งพา Tor สำหรับงานสำคัญควรประเมินช่องทางสำรองและเฝ้าระวังความพร้อมใช้งานโดยไม่ลดทอนข้อกำหนดความเป็นส่วนตัว

5. งานวิจัยพบ Secret ใน Public Container Image ถูกนำไปใช้ภายในไม่กี่วินาที

Docker HubCloud KeysContainer Security

การทดลอง Honeypot 300 Image พบ AWS Key ถูกเรียกใช้เร็วสุด 7.86 วินาทีหลังเผยแพร่ และ AWS Key ทั้ง 100 ชุดถูกใช้ภายใน 15 นาที

สถานะ: Research Confirmed; Registry Risk Ongoingเผยแพร่: 17 พ.ย. 2569
ดูรายละเอียดสถานการณ์ ผลกระทบ และข้อเสนอแนะ

สถานการณ์

นักวิจัย Stony Brook University เผยผลการทดลองสี่เดือน โดยเผยแพร่ Honeypot Container Image รวม 300 รายการใน Registry สาธารณะแปดแห่ง พร้อม Secret ล่อ เช่น AWS, OpenAI และ Anthropic API Key งานวิจัยพบการดึง Secret แบบอัตโนมัติจาก Image Layer โดยแทบไม่ต้องรัน Container และเรียกกลุ่ม Scanner เหล่านี้โดยรวมว่า ContainerBots โดยไม่ได้ยืนยันว่าเป็นผู้ปฏิบัติการกลุ่มเดียวกัน

ผลกระทบ

Image ถูกดึงมากกว่า 75,000 ครั้ง และ AWS Key ล่อได้รับ API Call มากกว่า 140,000 ครั้งจากประมาณ 5,000 IP โดย Docker Hub มีสัดส่วนกิจกรรม AWS เกือบทั้งหมด เวลาการใช้ AWS Key เร็วสุดคือ 7.86 วินาที ค่ากลาง 51.19 วินาที และ Key ทั้ง 100 ชุดถูกใช้ภายใน 15 นาที ผลนี้ยืนยันว่า Secret ที่ Push สู่ Public Registry ควรถูกถือว่ารั่วทันที

ข้อเสนอแนะ

หยุดเก็บ Secret ใน Dockerfile, ENV, Build Argument และ Image Layer ใช้ BuildKit Secret Mount หรือ Secret Manager แทน สแกน Image ก่อน Push และใน Registry พร้อมบล็อก Pipeline เมื่อพบ Credential หากพบ Secret ใน Image สาธารณะให้เพิกถอนและออกใหม่ทันที ไม่ควรเชื่อว่าการลบ Tag เพียงอย่างเดียวเพียงพอ

ทีมวิจัยนำโดย Alon Hertz จดโดเมน hexgrad.com ซึ่งปรากฏในไฟล์สาธารณะของโครงการ Kokoro แล้วใช้โดเมนดังกล่าวรีเซ็ตรหัสผ่านบัญชีผู้เผยแพร่บน Hugging Face จากนั้นสาธิตในสภาพแวดล้อมควบคุมว่าสามารถ Fine-tune Weight ให้โมเดลสร้างเสียงที่ต่างจากข้อความต้นทางได้โดยไม่แก้ Application Code

ข้อเสนอแนะ
